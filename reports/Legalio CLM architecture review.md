# Fixing Legalio's snapshot core before scaling

Legalio CLM is a broad, security-conscious multi-tenant contract manager whose newest modules are well built but whose original core rests on a design that cannot scale and a deployment path that has no safety net. The most important structural problem is that the backend loads every tenant's business data into one in-memory object and rewrites the whole projection on every save, which caps the system at one instance and makes write cost grow with total data volume ([server.ts](../apps/backend/src/server.ts), [POSTGRES_STORAGE.md](../POSTGRES_STORAGE.md)). The most important functional problem is that expiry reminders, the product's headline promise, are generated only at server start or by a manual superuser call, because nothing in the repo schedules them. The most urgent security problems are a Google sign-in path that never checks token audience, plaintext provider secrets in the database, and upload authorization derived from free-text record content. The deployment path pushes every commit on `main` to production over SSH with no build, lint or test gate ([deploy.yml](../.github/workflows/deploy.yml)). None of the findings is individually Critical, and the authorization core is genuinely strong, so the recommended order is to close the cheap, high-impact gaps in weeks 1-4 (CI, edge hardening, reminders, secrets, sign-in), then spend a quarter replacing the snapshot persistence model, and only afterwards invest in feature breadth such as obligations, e-signature and SSO. Effort figures below are reviewer estimates, not measurements; no load tests, penetration tests or production-host inspection were possible.

## The strong authorization core sits on a fragile persistence model

The backend is one Express 4 process whose `server.ts` runs to **7,524 lines and 115 inline route registrations**, about 43% of all backend source ([backend notes, apps/backend/src](../apps/backend/src/server.ts)). Newer features (documents, approvals, organization admin, auth console) are factory-style routers that take `sql` as an argument and are unit-testable, while the original CLM domain of partners, contracts, insertion orders, spendings and evaluations remains inline and untestable except through two long end-to-end scripts. Authorization is the standout strength: a declarative deny-by-default route-policy table runs before every business route, tenant context is re-verified against the database on every request, foreign resources return 404, SQL is parameterised, and the audit actor is overwritten with the verified identity ([routePolicies.ts](../apps/backend/src/routePolicies.ts), [identity.ts](../apps/backend/src/identity.ts)). The security review found no direct cross-tenant IDOR on the main CRUD routes.

The weakness is underneath. At boot `loadCoreData()` reads all rows of every business table for all organizations into a process-global `db`; every mutation edits that object and calls `saveDb()`, which clones all collections, fingerprints every row, upserts the changed ones, and deletes any database row absent from memory ([lib/auth.ts](../apps/backend/src/lib/auth.ts), [normalizedCoreStore.ts](../apps/backend/src/normalizedCoreStore.ts)). Saves are serialised by one promise chain, so all writes system-wide are single-file. The consequences are linear growth in CPU and memory per save, implicit deletes that let a stale or partially loaded `db` remove data, IDs generated from in-memory max-plus-one across all tenants, and the project's own instruction to "run one instance only". The frontend mirrors the design: `/api/init-data` ships every contract, partner, IO, spending and evaluation in one payload, then refetches the whole thing after each mutation, with search and sorting done client-side ([useWorkspaceData.ts](../apps/frontend/src/features/workspace/useWorkspaceData.ts)). The reviewers could not measure where this breaks and estimate low tens of thousands of rows per tenant across many tenants; that figure is an inference.

Several smaller data-layer defects compound this. Schema is created by `CREATE TABLE IF NOT EXISTS` on every boot with no versioned migrations, even though a `schema_migrations` table exists unused ([schema.ts](../apps/backend/src/schema.ts)). Dates are stored as text and JSON as text rather than `timestamptz` and `jsonb`; the newer document and approval tables carry no foreign keys. The pg pool uses library defaults with no connection timeout, so a stuck database hangs requests indefinitely ([node-postgres Pool docs](https://node-postgres.com/apis/pool)). Search is an `ILIKE` sequential scan per organization. Because two backend instances would silently overwrite each other, horizontal scaling and zero-downtime deploys are both unavailable until the model changes.

The recommended path is incremental, not a rewrite. Peel one entity at a time (contracts first, as the hottest) into a repository behind the same `{ db, ... }` factory pattern already proven in `documentRoutes.ts` and `approvalRoutes.ts`, using direct `INSERT/UPDATE ... WHERE organization_id = ?` statements, explicit deletes and per-organization sequences, while the in-memory `db` serves as read-through until the last entity is cut over. The reviewers estimate about one week per entity plus cutover, roughly **3-6 weeks** in total. In parallel, adopt a versioned migration runner guarded by an advisory lock (3-5 days), then convert date and JSON columns in forward migrations (1-2 weeks). Quick wins that need no redesign are pool `connectionTimeoutMillis`, `statement_timeout` and an explicit `max` (half a day), a `pg_trgm` index for search, and batching child writes. Splitting `server.ts` into domain routers (partners, contracts, IOs, spendings, evaluations, bulk-import, AI) follows naturally and should ride along with each repository extraction rather than as a separate project.

## Eight security gaps cluster at the edges, not the core

The security review rated six items High and none Critical (a seventh, open first-run setup, is accepted by design; see below); the nearest to Critical needs a precondition. The one nearest to Critical is Google sign-in: `/api/auth/google/sync-session` is public and proves an email by calling Google's `userinfo` with a caller-supplied access token, but never checks the token's audience, so a valid token issued to any other OAuth app the victim used can mint a 30-day Legalio session for that email, including superusers ([server.ts](../apps/backend/src/server.ts), lines 1919-1936 and 5611-5667). The fix is to verify audience via `getTokenInfo` or ID-token verification, and it is a day of work. Open first-run setup is accepted by design and is not counted as a finding: `POST /api/system/database` and `POST /api/system/setup` are unauthenticated until a superuser exists, so whoever reaches a fresh instance first can create the administrator and register their own object-storage bucket. The project owner confirmed this is intentional for a self-hosted installer, so the only exposure is the window before the superuser exists. The handover flags this for the new production deployment, which will start with an empty database ([HANDOVER_POSTGRESQL_COS.md](../HANDOVER_POSTGRESQL_COS.md)). Operationally, complete setup before the public URL is reachable (or over localhost or an SSH tunnel); an optional `SETUP_TOKEN` enforced only when set would add a guard without changing the flow.

Brute-force protection is weaker than it looks. Better Auth's built-in limiter keys on client IP, is enabled by default only in production, and uses memory storage, while nginx appends to any client-sent `X-Forwarded-For` and Express sets `trust proxy: true`, so an attacker can rotate a forged leading address; there is no lockout, MFA or Express-level limiter, and email verification is not enforced ([nginx.conf.template](../apps/frontend/nginx.conf.template), [lib/auth.ts](../apps/backend/src/lib/auth.ts)). Combined with an 8-character minimum, credential stuffing is the most realistic account-compromise path. The shipped nginx also serves port 80 only, with no TLS, no security headers, no `limit_req`, and `/sys` publicly proxied. The remedies are cheap: set `X-Forwarded-For $remote_addr`, pin the proxy hop count, configure Better Auth rate rules with durable storage, add nginx rate limits and headers, restrict `/sys` by allowlist or VPN, and add helmet-equivalent headers in Express. Together this is roughly **2-3 days** plus TLS configuration.

Two High findings concern data at rest and tenant files. SMTP passwords, the Gemini key and Google access and refresh tokens are stored as plaintext JSON in `app_settings`, so any database dump carries them; the handover lists encrypting them as out of scope ([coreDataStore.ts](../apps/backend/src/coreDataStore.ts)). The existing AES-256-GCM `secretBox` already seals Google and COS credentials, so extending it is 2-3 days, ideally with a key-id envelope and a key separate from `BETTER_AUTH_SECRET`, because rotating that secret currently destroys stored credentials. Separately, `/uploads` authorization works by scanning every record's JSON for any `/uploads/...` string and treating the record's holder as owner. A user in tenant B can paste a guessable tenant A path (built from organization name, vendor name and a deterministic file name) into their own record and read the file ([server.ts](../apps/backend/src/server.ts), lines 364-465). This is High for hosted multi-tenant use and Medium for single-organization installs. The fix is a server-written uploads table recording key, organization, record and uploader at save time, plus random organization-id-based keys.

The compliance gap is the operational activity log, which is truncated to the newest **500 entries across all organizations** and triggers a whole-database save per entry, so one noisy tenant evicts everyone's history and document views and downloads are never logged ([server.ts](../apps/backend/src/server.ts), lines 1738-1776). The structured `audit_log` table should become the single record, uncapped and per-tenant, with retention settings. Medium items worth scheduling after these are: enforcing email verification and `emailVerified` on invitation acceptance (to stop pre-registration of invited addresses), revoking sessions on password reset, moving session tokens out of `localStorage`, server-side HTML sanitisation of stored contract content, upload type validation, department scoping for documents and approvals, and Postgres row-level security as defence in depth, because all tenants share one in-memory object and isolation depends on every handler remembering `assertRecordAccess`. A CI test that enumerates `ROUTE_POLICIES` and asserts cross-tenant 404s would protect the strongest part of the design cheaply.

## Reminders never fire, and AI has no budget

The most important functional defect is that `recalculateStatuses()`, the only code that creates reminder notifications and emails, is invoked at server start, after settings changes, organization reset, bulk import, and by `POST /api/cron/trigger-check`, which requires a superuser session; no scheduler exists in the backend, compose file, scripts or CI ([server.ts](../apps/backend/src/server.ts), lines 1241, 5475, 5922, 6390, 6938). In practice reminders fire when someone redeploys. The logic is also brittle: it matches the exact day count (default 90, 60, 30, 14), so a missed day loses that reminder permanently; it dedupes by record and offset forever, so renewed contracts never re-notify; there is no reminder keyed to the notice-period deadline itself; and email is sent fire-and-forget with `is_sent` set before sending and with SMTP certificate validation disabled. Buyer guidance treats renewal alerts as meaningful only when tied to a lead time, a named owner and a next action ([ContractSafe](https://www.contractsafe.com/blog/best-contract-lifecycle-management-software-features-2026)). The fix is small relative to its value: a daily in-process scheduler under an advisory lock, running per organization in tenant timezone, using window comparisons and a sent-offsets ledger keyed by record, end date and offset, plus a notice-deadline reminder and a persisted outbox with retry. Estimated **2-4 days**, and it should be the first functional change shipped.

Beyond reminders, the lifecycle model is sound where it matters most. Contract status is computed from dates and termination, termination validation is shared by form and API, and the approval engine uses guarded `UPDATE ... WHERE status='pending' AND current_step=?` statements that block step-skipping and double decisions. Gaps are in business invariants rather than tenancy: `PUT /api/contracts/:id` spreads arbitrary body fields over the record, the contract "approval status" label is not linked to the approval engine (which applies only to editor documents), no gate stops contracts for partners with incomplete due diligence, approvals send no email and have a stored SLA with no escalation, and auto-renewal silently moves the end date without a renewal record.

AI is used widely and mostly sensibly: extraction returns to a review form rather than persisting, responses use structured JSON schemas, chat context is tenant- and department-scoped with direct identifiers stripped, and the text-first OCR pipeline (digital text extracted locally, vision only for scanned pages, SHA-256 caching) is a genuine differentiator for a lite product. The gaps are cost and safety controls. There is no per-user or per-organization rate limit, token budget or usage log. Chat stuffs the entire visible workspace as JSON into every request with unbounded client history. The model fallback chain tries up to six models sequentially with a 35-second timeout each, the timers are never cleared and the requests are never aborted, so worst case is minutes of blocked HTTP handler and continued billing. PDF and OCR work runs on the main event loop, which Express guidance advises offloading to worker threads ([Express performance best practices](https://expressjs.com/en/advanced/best-practice-performance.html)). Privacy depends on the tier of the customer's Gemini key: Google's terms state unpaid-tier content may be used to improve its products while paid-tier content is not ([Gemini API Additional Terms](https://ai.google.dev/gemini-api/terms)), and the app neither checks nor warns. The OCR cache key also lacks an organization id, and the reviewers could not verify that the hard-coded Gemini model names exist, so model lists should move to configuration. Priority fixes: per-organization limits and usage metering (3-5 days), abortable calls with 429 backoff and a configurable model list, retrieval or function-calling chat in place of workspace dumps, provenance (page and quote) for extracted fields, and long OCR as background jobs.

## Frontend: a 1.9 MB entry chunk and an App.tsx doing the server's job

The frontend is React 19, Vite 6 and Tailwind 4 with route-level lazy loading, but the measured build shows an **entry chunk of 1.92 MB raw (about 560 kB gzip, 419 kB brotli)** and a 1.09 MB editor chunk. The likely cause is three i18n catalogs (roughly 700 kB of source, including a 148 kB inline dictionary in `LanguageContext.tsx`) imported statically for every user regardless of language; that attribution is an inference because no bundle visualizer has been run. The Vite warning limit was raised to 800 kB, masking the problem, and the nginx template does not enable `gzip_static` or `brotli_static` or long-cache headers, so the pre-compressed assets the build emits may not be served. Lazy-loading non-active languages, adding a visualizer and restoring the default limit is a **2-3 day** task with a large payoff.

Data handling is the second theme. TanStack Query is used in only six files; elsewhere 107 raw `fetch` calls across 44 files, duplicated `request<T>()` helpers, and a 1,112-line `App.tsx` that hand-writes optimistic updates, rollback and full refetch for each entity. Types are shared compile-time through `@legalio/types`, but nothing validates payloads at runtime, and `MainApp` calls hooks after an early `return null`, a rules-of-hooks violation that works only by accident. The repo has no ESLint at all, which explains how such defects survive, and TypeScript is non-strict with 142 `any` uses in the frontend. The recommended sequence is: fix the hook order and add ESLint with `react-hooks`, `jsx-a11y` and the TypeScript promise rules (1-2 days); centralise a single API client and move to `useMutation` with targeted invalidation, dropping the client-sent `userEmail` and `userRole` fields (5-8 days); then introduce server-side pagination and search to replace `/api/init-data` (8-12 days, coupled to the backend repository work), with a real router offering record deep links.

The largest components are maintainability risks with no test net: `ContractDocumentEditor.tsx` is 2,516 lines with 31 `useState` and no memoization, and the frontend has 14 pure-logic test files but no component, end-to-end or accessibility tests (two existing test files are not even in the hand-listed `npm test` script). Accessibility foundations are decent (Ark UI primitives, over 1,000 `aria-` attributes) but there is no skip link, `index.html` carries a stale title and fixed `lang="id"`, there is a single root error boundary so one render error blanks the app, and conformance is unverified. i18n is complete for Indonesian and English (3,589 keys) with 33 Chinese keys missing, but many call sites embed Indonesian defaults. The component library carries 34 facade modules with no external importers, an upper bound since internal use was not checked, and a README that points to nonexistent docs; pruning is low priority because unused modules do not reach the bundle. The user-facing "AI Redlining" is a risk review, not tracked changes, and should be renamed or complemented with word-level diffing.

## DevOps: no gate, no rollback, no restore procedure

The monorepo itself is healthy: `npm ci` installs 679 packages in 22 seconds, lint (which is only `tsc --noEmit`) and build pass, and 76 of 78 unit tests passed in the reviewer's sandbox. The two failures were consistent with that sandbox's passwordless `trust` authentication and were not independently confirmed as defects. The deployment path is the gap. `deploy.yml` runs on every push to `main`, writes an SSH key and runs `ssh user@host` with no command, so the real deploy script lives on the Tencent Lighthouse host, invisible to the repository; there is no build, test, scan, smoke check, image registry or rollback, while the handover's own mandatory gate (lint, build, test, build of the console, two end-to-end suites) is manual. Compounding this, `.gitignore` excludes `.github/`, `.dockerignore`, most scripts and `docs/`, so any new workflow is silently dropped unless force-added, and the handover warns that merging to `main` deploys to a production database that starts empty ([HANDOVER_POSTGRESQL_COS.md](../HANDOVER_POSTGRESQL_COS.md)). `npm audit` reports **three high-severity direct dependencies**: dompurify (installed 3.2.6, with XSS advisories and relevant to rendered contract HTML), nodemailer (including a cross-tenant SMTP credential disclosure advisory) and vite, all with fixes available.

Operational basics are thin. Logging is raw `console.*` (74 calls in `server.ts`) with no request IDs or error tracking; `/api/health` does not query the database and neither Dockerfile nor compose uses it; graceful shutdown force-exits after 3 seconds without draining the save queue or closing the pool; the global error handler returns raw `err.message` to clients. Backup guidance is a single `pg_dump` example with no schedule, off-site copy or tested restore, and the Drive backup index lives in a local file on the data volume. Because `BETTER_AUTH_SECRET` encrypts stored credentials, losing it is a data-loss event that no document tells operators to guard. The Docker images copy the whole repo before `npm ci` (no layer caching), pin neither base images nor `nginx` and `postgres` tags, and run nginx as root. Documentation is a 56 kB Indonesian handover journal with Codespaces-specific paths rather than a runbook, and the README claims an MIT license without a `LICENSE` file.

The first week of DevOps work should be: un-ignore `.github/`, add a pull-request workflow running install, lint, build and tests against a Postgres service container, make deployment depend on it, and commit the deploy script with a health check and rollback (roughly 3-5 days combined); run `npm audit fix` and add Dependabot or Renovate (under a day); make the health endpoint run `SELECT 1` and add compose healthchecks; adopt structured logging with request IDs and an error tracker; and write a backup and restore runbook with scheduled `pg_dump` or managed snapshots, verified COS versioning and an off-server copy of the secret. Express 5, dotenv 18 and similar major upgrades are low urgency. The one unresolved dependency is the unseen server: TLS termination, firewall, cron jobs and snapshots on the Lighthouse host could not be assessed, and some "missing" items may exist there.

## A four-phase roadmap sequenced by risk and dependency

The ordering below follows two principles: cheap fixes that remove acute risk go first because they do not depend on the persistence rewrite, and feature work waits until the platform can support it. Timings are reviewer estimates for a small team and assume the persistence work is the long pole.

| Phase | Window | Scope | Why now |
|---|---|---|---|
| 0. Safety net | Weeks 1-2 | PR CI gating deploy, un-ignore `.github/`, deploy script and rollback in repo, `npm audit fix` and Dependabot, nginx `X-Forwarded-For` fix, rate limits, security headers and TLS, deep health check, backup and restore runbook | Nothing else is safe to ship without a gate; edge exposures are the cheapest serious risks |
| 1. Correctness quick wins | Weeks 3-6 | Reminder scheduler with ledger and outbox, Google audience verification, seal SMTP, Gemini and Google tokens, uploads ownership table and random keys, uncapped per-tenant activity log, error-message redaction and pino logging, pool timeouts, ESLint with promise and hooks rules plus the `MainApp` fix, AI limits and abortable calls, per-language i18n loading | Each is days of effort and closes a High finding or the headline functional defect |
| 2. Persistence and structure | Weeks 7-18 | Versioned migrations, repository-per-entity replacing snapshot sync (contracts first), server-side pagination and search replacing `/api/init-data`, central API client with `useMutation`, split `server.ts` and `App.tsx`, zod validation and unified error codes, field whitelisting on PUT, RLS and cross-tenant route tests, component and Playwright smoke tests | Removes the single-instance, O(N)-save and lost-update hazards; enables multi-instance and zero-downtime deploys |
| 3. Product depth | Months 5-8 | Obligation and key-date tracking with AI extraction and human confirmation, e-signature integration or signed-copy webhook, public API with keys and outbound webhooks, tenant data export, OIDC SSO, clause library tied to existing policy-pack `clauseRules`, approval email notifications with SLA escalation, retrieval-based chat, scheduled digest reports | Builds on a platform that can now carry features; matches what buyer guides treat as differentiators |

Phase 3 priorities come from the functional review's gap analysis against buyer guides and analyst commentary, which are mostly vendor sources and may carry commercial bias ([ContractSafe](https://www.contractsafe.com/blog/best-contract-lifecycle-management-software-features-2026), [Bindlegal](https://bindlegal.com/resources/guides/clm-market-report-gartner-forrester/)). Notably, ContractSafe advises lite buyers to start with repository and alerts and defer e-signature, intake and integrations, which supports putting reminders ahead of everything in Phase 1. The same guidance asks that AI show its source text and keep a human review step, which argues for provenance on extracted fields. For the Indonesian market, a local e-signature provider is a plausible integration target, though no market data was gathered to confirm it.

## Conclusion

The review's central insight is that Legalio's risks are not where its code looks worst. The 7,500-line `server.ts` is ugly but works; the dangerous parts are a persistence model that silently ties the product to a single process, a deploy pipeline with no brakes, and a handful of well-bounded authentication and secret-handling gaps beside an otherwise exemplary authorization design. That shape makes the remediation unusually tractable: roughly a month of focused, low-risk work removes every High-rated security item and the reminder defect, while the genuinely large investment is concentrated in one place, the repository extraction in Phase 2, which also unlocks scale, testability and the split of `server.ts` as side effects.

Two caveats bound these conclusions. First, the evidence is static: no load test, penetration test, EXPLAIN run, end-to-end suite, Docker Compose run or inspection of the production host was performed, so scalability thresholds and any controls living on the Lighthouse server remain unknown. Second, the handover states that real object-storage setup, a clean `docker compose up` and the setup-rollback path are untested, and these should be exercised before the PostgreSQL branch is merged and auto-deployed to a production database that begins empty.
