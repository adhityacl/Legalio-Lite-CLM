# Legalio CLM backend architecture (apps/backend, branch PostgreSQL)

Evidence base: direct code read at HEAD ce6ecd8 (60 commits on branch). All paths are under /home/user/Legalio-Lite-CLM/apps/backend/src unless stated. Line numbers are from the checked-out files.

## 1. Overall structure, modularity, coupling, testability

### Takeaway
The backend is a single Express 4 process with a very large, procedural `server.ts` (7,524 lines, 115 inline `app.*` route registrations) that owns routes, business logic, AI calls, Drive sync, mail and an in-memory copy of all business data. Newer code (documents, approvals, org admin, auth console, route policies, RBAC, object store) is cleanly split into factory-style modules that take `sql` as an argument and are testable; the legacy core (partners, contracts, IOs, spendings, evaluations, templates) is not.

### Cited Findings
- Source totals: ~17.5k lines in src; server.ts alone is 7,524 (43%). Next largest: organizationAdminRoutes.ts 814, googleDriveSync.ts 729 (lib), cheapOcrPipeline.ts 694 (lib), authConsoleRoutes.ts 673, documentRoutes.ts 556 (wc -l).
- server.ts has 115 `app.get/post/put/patch/delete/use` calls. The legacy CRUD for partners (L2213-2714), evaluations (L2714-2955), spendings (L2980-3566), contracts (L3838-4900), IOs (L4902-5440), bulk-import (L6443, ~500 lines), AI parse/review endpoints, tenants (L6954-7080), chat (L7102), setup (L7310) are all inline in it. Helpers for Gemini retry (L890), reminders/mail (L1456-1610), lifecycle (L1614-1736), Drive folders (L216-340, L619-737), upload ACL (L370-465) are also inline.
- Extracted modules mounted from server.ts: `createGoogleCredentialsRouter` (L4510), `createDocumentRouter` (L4513, 18 routes), `createApprovalRouter` (L4515, 7 routes), `createOrganizationAdminRouter` (L7476, 29 routes), `authConsoleRouter` (L7503). They use dependency injection (`{ db: sql, tenantOf }`) which makes them unit-testable (approvalRoutes.test.ts exists).
- `server.ts` has module-level mutable state: `let db: any` (L707) holding all tenants' partners/contracts/ios/spendings/etc; `uploadIndex` (L~395), `lifecyclesFreshUntil`, `driveBackupTimer`, `storageCache`. `export { app, ... }` (L7524) and `export async function init()` (L1149) mean importing server.ts for tests pulls the whole app; the server tests are therefore HTTP e2e (normalizedCore.e2e.ts spawns the server) rather than unit tests.
- Type discipline: `let db: any`; 122 occurrences of `: any`/`as any` in server.ts; `__name(...)` esbuild helper leaked into source (L10, L942, L1141, L3091); tsconfig (packages/ts-config/base.json) has no `strict` -> HANDOVER_POSTGRESQL_COS.md §2 admits "tsc does not catch promises used as booleans... can produce authorization bypass" and a manual "promise check" is part of the gate; 4 such bypasses were found in review (§3 "Fase B").
- Authorization design is a strength: `routePolicies.ts` is a declarative default-deny table (L1-120: public / identity / router / platform / tenant / orgParam kinds); `createAuthorizationMiddleware(sql)` is mounted at server.ts L176 before any business route; CSRF-style same-origin check for cookie sessions at routePolicies.ts L285 using `isSameOriginRequest` (identity.ts L144). `rbac.ts` (337 lines), `recordScope.ts` (department scope) are separate and small.
- Bootstrap: `main.ts` (126 lines) is a thin shell app that handles `POST /api/system/database` onboarding, lazily `import('./server')` after a DB connection works, returns 503 DATABASE_REQUIRED otherwise (main.ts L60-90), exits 1 if a configured DB is down (L95-103), graceful SIGTERM with 3s force-exit (L105-119).
- Many handlers read `req.body` fields unvalidated and in mixed languages (Indonesian and English error strings), e.g. POST /api/partners L2464-2568 only checks `partner_name`; there is no schema validation library (grep for zod/joi/ajv/helmet/rate-limit/pino/winston in src: no hits). Hand-rolled sanitizers exist (`sanitizePartnerTags`, `sanitizeIdentifiers`, `sanitizeCountryCode`, `parseCosConfig`, `parseDatabaseConfig`, `validateSpendingAllocations`).
- Dead/stub code: `triggerAutoPushToGoogleSheet` is a no-op returning `Promise.resolve()` (L1409) yet is still called from handlers (e.g. L2563).
- Express 4.21 is used (package.json); the repo wraps routes with `forwardAsyncRouteErrors` (asyncRoutes.ts, 14 lines) because Express 4 does not forward rejected promises; it is applied to the app and the document/approval/googleCredentials/authConsole routers.

### Inferences
- Modularity is bimodal: new features were added as injectable routers; the original CLM domain was never extracted. The lowest-risk refactor is to peel off one entity router at a time (partners, contracts, ios, spendings, evaluations, bulk-import, AI) behind the same `{ db, ... }` factory pattern already proven in documentRoutes/approvalRoutes.
- Because handlers mutate the global `db` object then call `saveDb()`, route code cannot be tested without the whole server or a rewrite to repositories.

### Gaps
- No docs/rbac/tenant-boundaries-endpoint-inventory.md was found (routePolicies.ts header says the table is its source); not verified whether it is generated.

## 2. Data layer (PostgreSQL)

### Takeaway
The PostgreSQL migration is competent at the SQL-facade level (ambient AsyncLocalStorage transactions, savepoints, placeholder translation, advisory locks, batched child reads), but the core CLM data still follows an "in-memory full snapshot, diff-and-write-everything" model that does not scale, has a lost-update / multi-instance hazard, and there is no real migration system.

### Cited Findings
- `db.ts` (189 lines): `sql = {get, all, run, exec, tx, inTx}` over a `pg.Pool` (L~60-130). Transactions are ambient via `AsyncLocalStorage`; nested `tx` -> `SAVEPOINT sp_n`; a client that cannot ROLLBACK is destroyed (`client.release(broken)`). Placeholder translator `toPg` converts `?` and `@name` to `$n`; outside production it throws on unquoted camelCase identifiers or bare `user` (L~45-52) - a guard against pg case-folding.
- Pool is created with `new pg.Pool(config)` with no `max`, `idleTimeoutMillis` or `connectionTimeoutMillis` (db.ts `connect()`), i.e. pg defaults: max 10, idle 10s, no connection timeout ([node-postgres Pool docs](https://node-postgres.com/apis/pool)). Idle-error handler is present. The better-auth library shares the same pool (`authOptions(pool())`).
- Type parsers are per-query (timestamptz -> ISO string, int8 -> Number if safe), not global.
- Schema: `schema.ts` `ensureSchema()` runs on every boot: better-auth `getMigrations().runMigrations()`, then `CREATE TABLE IF NOT EXISTS` blocks (schema.ts L12-110). A `schema_migrations` table is created but unused (HANDOVER "Out of scope: tabel schema_migrations"; POSTGRES_STORAGE.md: "Every statement is idempotent"). Consequence: no versioned/forward migrations, no ALTER path for existing installs, no down/rollback, no concurrent-boot protection (two starting instances race on DDL).
- Business tables (normalizedSchema.ts, `ENTITIES`: partners, contracts, insertion_orders, spendings, evaluations, notifications, activity_logs, templates) are generated by `createNormalizedCoreSchema` (normalizedCoreStore.ts L28-108). Design traits: `TEXT PRIMARY KEY` on the business key alone (e.g. `partner_id`), with `UNIQUE(organization_id, key)` and composite FKs `(organization_id, partner_id)` deferred; `extra_json TEXT` catch-all column per row; dates stored as TEXT (`created_at text`, `start_date` text); money as `bigint minor + scale` (good - avoids float); booleans as `INTEGER CHECK IN (0,1)`; JSON as TEXT not jsonb; `record_position` integer preserving array order.
- Other tables also store dates as text and have no FKs: `contract_documents`, `contract_drafts`, `contract_comments`, `approval_*` (schema.ts L60-100; documentRoutes.ts header comment: "They have no foreign keys, so deletes cascade by hand"). Payload tables (`allowed_users`, `branding`, `app_settings`, `news_ticker`) store JSON as `text payload`. `approval_requests.file_data bytea` stores uploaded approval files in the DB while other uploads go to COS.
- Indexing: reasonable composite indexes for business tables (`idx_v3_*`, normalizedCoreStore.ts L52-64) and documents (schema.ts). `search_records` has only a btree on (organization_id, entity_type, entity_id); search is `(title || ' ' || body) ILIKE ALL(?)` = sequential scan per org (normalizedCoreStore.ts L~283-290, flagged `shortcut:`; POSTGRES_STORAGE.md acknowledges and names pg_trgm/tsvector as upgrade path).
- **Core persistence model (highest-impact finding):** `loadCoreData()` (lib/auth.ts L107-125) reads ALL rows of every business table for ALL organizations into the process-global `db` object at boot (server.ts L1170). Every mutation does `db.partners.unshift(...); await saveDb()` (e.g. L2558-2559). `saveDb()` (L1398) -> `coreSaver.save()` -> `structuredClone` of all collections -> `synchronizeBusinessRows` (normalizedCoreStore.ts L~215-262), which, for every entity in every org, fingerprints each row (sha1 of JSON) vs a cache and, per changed row, upserts + `writeChildren` (DELETE + INSERT per child), then does `SELECT key FROM table` (no org filter) and deletes any DB row not present in memory. Costs: O(total rows in all tenants) CPU/memory per save even for a 1-row edit; unchanged rows skip SQL only thanks to the in-process fingerprint cache (`syncedRows` WeakMap). Saves are serialized in-process by a promise-chain lock (coreDataStore.ts `createCoreSaver`, L~85-120), so all writes system-wide are single-file.
- Correctness hazards of that model: (a) deletes are implicit ("not in memory = delete"), so a stale or partially loaded `db` can delete data; (b) a second backend instance, or any out-of-band SQL write, is invisible/overwritten - POSTGRES_STORAGE.md "Operations" states "Run one instance only"; (c) IDs are generated from in-memory max+1 across all orgs (`generateNextPartnerId` L1275-1292, same for contract/IO/spending) and are global primary keys, so concurrent requests rely on "no await between generate and push" convention (HANDOVER Fase C "Aturan ID") - fragile; (d) `recalculateStatuses()` saves the whole DB (comment at L6938 "once per import: it saves the whole database").
- Transactions are used correctly where the newer modules need atomicity: `lockDocument` row lock + conditional `UPDATE ... WHERE status='pending' AND current_step=?` with `changes===1` check in approvalRoutes (HANDOVER Fase B fixes 1-3, 6); `pg_advisory_xact_lock` for setup, approval codes, admin invariants (HANDOVER D2 "Lock"); `FOR UPDATE` for org settings. Only 6 `sql.tx` uses in server.ts (L5956, 6299, 6985, 7046, 7338) vs 7/3/11/9 in documentRoutes/approvalRoutes/organizationAdminRoutes/authConsoleRoutes.
- N+1: addressed for reads in Phase E: `childArrays` issues one `WHERE fk = ANY(?)` query per child table (normalizedCoreStore.ts L~175-205); list costs partners 5, contracts 2, spendings 3 queries (HANDOVER Fase E, with a test "a list read costs one query per table"). Writes still do DELETE+INSERT per child item and per-id stale deletes (HANDOVER Fase E "Belum dioptimalkan"). No pagination: list endpoints return arrays from memory; only documentRoutes has PAGE_SIZES paging. `ORDER BY/LIMIT` appear in only a handful of server.ts queries.
- Test DB isolation is good: `testDatabase.ts` creates `legalio_test_<random>` DBs and drops them; `clientConfig` refuses non-`legalio_test_*` names in APP_TEST_MODE (db.ts).
- SQL injection posture: values are parameterized; identifiers in generated SQL come from static ENTITIES and are quoted by `q()`.
- Credentials at rest: `integration_credentials` AES-256-GCM via secretBox.ts with key HKDF'd from BETTER_AUTH_SECRET (secretBox.ts, 21 lines); POSTGRES_STORAGE.md warns changing the secret makes them unreadable. HANDOVER lists as out of scope: encrypting `smtpPassword`, `geminiApiKey`, `refreshToken` stored in `app_settings` payload (plaintext JSON).
- docs: POSTGRES_STORAGE.md (backup via `pg_dump`, COS versioning, "Old SQLite data is not imported"); HANDOVER_POSTGRESQL_COS.md (status 22 Oct 2026, phases A-G done; "Belum dites: docker compose up lengkap; rollback tx setup restoring COS cache"; "do not merge to main before phase G" since deploy.yml deploys main to production and production will start with an empty PostgreSQL).
- Docker/compose: compose.yaml has postgres:17 with healthcheck and volume, backend `depends_on: service_healthy`, port 3000 bound to 127.0.0.1; default `POSTGRES_PASSWORD:-legalio` fallback; `restart: unless-stopped`. Backend Dockerfile is multi-stage node:22-bookworm-slim, runs as `node` user, `npm prune --omit=dev`, no HEALTHCHECK instruction, `/data` volume.

### Inferences
- The snapshot-sync design was a pragmatic bridge from the SQLite/JSON-blob era (the handover calls it "model penyimpanan inti: koleksi in-memory tetap dipakai"); it works for a single-tenant-sized dataset but is the main scalability and data-loss risk. Tail latency grows linearly with total rows because of structuredClone + fingerprint hashing of every row on each save.
- Using Postgres only as a persistence layer for an in-memory model forgoes its strengths (indexes, constraints, concurrency); per-entity repositories with direct `INSERT/UPDATE ... WHERE organization_id=?` and `RETURNING`, sequences (or `organization_id`-scoped counters) for IDs, would remove the single-writer lock, the cache, and the single-instance rule.
- Default pg Pool max 10 with no connection timeout is adequate for one node today but a stuck DB would hang requests indefinitely; set `connectionTimeoutMillis`, `statement_timeout`, and a sized `max`.

### Gaps
- Did not run EXPLAIN against a populated DB; indexing assessment is by reading DDL only.
- Did not measure actual save latency vs row count.

## 3. Object storage (COS), Google Drive sync, OCR/AI pipeline, background jobs

### Takeaway
Object storage is well abstracted and security-conscious; Drive sync and AI/OCR are workable but ad hoc, with in-process timers and no durable job queue. Scheduled reminders are not actually scheduled.

### Cited Findings
- `objectStore.ts` (99 lines): `ObjectStore {put,get,delete,list}` Buffer-based interface, `memoryStore()` for tests, `cosStore()` over `cos-nodejs-sdk-v5` with prefixing, paginated `list` (MaxKeys 1000, Marker), SDK `Timeout: 60000`; `parseCosConfig` validates bucket/region regexes so the SDK host cannot be redirected; `probe()` does put/get/delete before credentials are saved; `keyFromLink` rejects `..`, `\`, NUL and dot-segments. Tests: objectStore.test.ts (95 lines).
- Serving: `/uploads` goes through `authorizeUpload` (server.ts L400-428) - resolves identity, finds owning records via `uploadOwners`, checks org context + `document.view` + record visibility (dept scope), sets `nosniff`, `CSP: sandbox`, `no-store`; then `serveUpload` (L430) reads the full object into memory and `res.send(body)` - no streaming and no HTTP Range (HANDOVER: Range support out of scope). Upload cap: multer memoryStorage 30 MB (L141-144) and `express.json` 25 MB (L145), so up to ~30 MB per request is held in RAM; there is no concurrency limit.
- Upload keys are `<Org name>/<Partner>/<Folder>/<file>` derived from names (POSTGRES_STORAGE.md; HANDOVER notes this as a "masalah lama"; server.ts comment L~375 that two orgs can sanitize to the same folder name).
- Deleting a COS object has no admin endpoint; application reset deletes keys one request per object (POSTGRES_STORAGE.md).
- Google Drive: `lib/googleDriveSync.ts` (729 lines) + `lib/googleServiceAccountAuth.ts` (312) + `googleCredentials.ts` (206). Folder/file creation with "self-healing" retries on 401/404 (googleDriveSync.ts L222-430), done synchronously inside request handlers (e.g. POST /api/partners creates up to 5 Drive folders before responding, server.ts L2480-2510, errors only `console.warn`). Drive backup of uploaded COS objects: `scheduleDriveBackup` (server.ts L560-575) is a debounced `setTimeout` (5s) with an in-memory `pendingDriveBackups` Set - lost on restart; index kept in `APP_DATA_DIR/drive-backup.json` (not in the DB). Startup runs `ensureAllPartnersFolders()` fire-and-forget (L~1225). Sheets sync is a stub (`triggerAutoPushToGoogleSheet` no-op, L1409; `/api/google-integration/sync` routes still exist L6083).
- OCR/AI: `lib/cheapOcrPipeline.ts` (694 lines): PDF inspection with pdf-lib/pdf-parse, digital-text extraction, legal-keyword scoring (`LEGAL_KEYWORD_TAXONOMY`), PDF page optimization, then Gemini via `@google/genai`; results cached in table `ai_ocr_cache` keyed by SHA-256 (`OcrMemoryCache` class is DB-backed despite its name, L62-117, with TTL 24h and size-based eviction; transcripts cached without TTL, L120-145). The cache key and table have no `organization_id`, so identical files across tenants share transcripts (low risk, but a cross-tenant side channel by design).
- Gemini call wrapper `generateContentWithRetryAndFallback` (server.ts L890-940): sequential fallback over 6 hard-coded model names, 35s per-attempt `Promise.race` timeout - the timer is never cleared and the underlying request is not aborted; no retry/backoff on 429; logs each attempt with console.log. Model IDs such as `gemini-3.7-flash` are hard-coded (L~897-904); I could not verify they exist, so treat as config-drift risk. PDF/OCR processing (pdf-parse, pdf-lib, hashing) runs on the main event loop (no worker threads); Express docs recommend offloading CPU-bound work to worker threads ([Express performance best practices](https://expressjs.com/en/advanced/best-practice-performance.html)).
- Background jobs: there is no job queue, scheduler or worker process. `setTimeout`/`setInterval` appear only for the Drive-backup debounce, the Gemini timeout and shutdown. Reminder emails/notifications come from `recalculateStatuses()` (L1614-1706), which is invoked: at boot (L1241), by `POST /api/cron/trigger-check` (L5474, policy `platform.database.optimize` i.e. superuser session only - routePolicies.ts), after platform config change (L5922), reset (L6390), and bulk import (L6938). No cron/scheduler is documented in README.md or .env.example (grep "cron|scheduler|reminder": no hits). Lifecycle statuses are refreshed lazily on reads with a 60-second memo (`refreshContractLifecycles`, L1710-1736). Net effect: expiry reminders fire only on restarts or when a superuser manually calls the endpoint, unless the operator externally authenticates a cron caller (not provided).
- Mail: nodemailer SMTP sent inline (`sendSmtpEmail` L1456), template store with `FOR UPDATE` (mailTemplateStore.ts, 31 lines); no outbox/retry.

### Inferences
- Failure modes: a process restart loses the pending Drive backup set and any in-flight AI call; there is no idempotent retry. For a single-node deployment this is tolerable, but jobs should at minimum be persisted (a `jobs` table with `SELECT ... FOR UPDATE SKIP LOCKED`, or pg-boss/graphile-worker) and reminders driven by an in-process or compose-level scheduler.
- Streaming COS `getObject` to the response (and signed URLs after authz) would cut memory per download.

### Gaps
- Did not verify real behaviour against Tencent COS or Google APIs (no credentials; handover also lists docker compose and COS rollback as untested).

## 4. Error handling, logging, validation, config/env, scalability

### Takeaway
Error handling is mostly "try/catch -> console -> 500 with message"; logging is raw console; validation is ad hoc; config is env + onboarding file. The system is explicitly single-node by design.

### Cited Findings
- Global error middleware (server.ts L7509-7522) logs `[API Unhandled Error]` and returns `err.message` and `err.status||500` to the client, i.e. internal messages (including DB/pg messages) can leak; no request id, no structured format. The `/api/*` 404 handler returns a different shape (`{error}`) than `sendError(req,res,status,CODE)` used in newer code (identity.ts), and legacy messages are Indonesian strings; `localizeApiMessages` (serverMessages.ts, 348 lines) translates by header `x-app-language`.
- Logging: 73 `console.*` calls in server.ts; no logger library (pino/winston absent), no request logging, no correlation ids. Express docs advise against synchronous console logging in production and recommend pino ([Express perf best practices](https://expressjs.com/en/advanced/best-practice-performance.html)). Activity/audit data is persisted (activity_logs entity; `audit_log` table with indexes in schema.ts; `appendAudit`), which is a positive.
- Swallowed errors: 107 `catch` in server.ts, 15 of the bare `catch {` / `catch (_` form; e.g. `/api/rbac/me` swallows context resolution failure (L188).
- Validation: no schema library; per-route manual checks; request bodies up to 25 MB JSON for every route (L145); `req.body.userEmail/userName/userRole` are still read from the body for activity logging in handlers (e.g. L2560) though `addActivityLog` says verified identity wins when present.
- Security middleware: no helmet, no rate limiting, no CORS config in the backend source (grep). `trust proxy` = true unconditionally (L~134) which is only safe behind a proxy; compose binds 127.0.0.1:3000 (compose.yaml) and the frontend nginx container is published on 8080. Auth rate limiting would come from better-auth if configured; I did not find explicit config.
- Config/env: `dotenv/config`; env keys include DATABASE_URL, BETTER_AUTH_SECRET (production exits if missing: main.ts), APP_DATA_DIR, PORT, APP_TEST_MODE, DEMO_ADMIN_*, GOOGLE_*, GEMINI_API_KEY, SYSTEM_CONSOLE_DIR, API_ONLY. No central typed config module (env read at point of use across files; runtimePaths.ts 36 lines holds only paths). `database.json` holds the DB password in plaintext with mode 0600 on the /data volume (db.ts `saveDatabaseConfig`). Secret fallback `'insecure-development-secret-change-me'` is used outside production (HANDOVER Fase C step 3).
- Health: `/api/health` (server.ts L7279) public; backend Dockerfile has no HEALTHCHECK; compose has none for backend.
- Deploy: .github/workflows/deploy.yml triggers on push to `main` and only SSHes to a Tencent Lighthouse host (`ssh ... "${SSH_USER}@${SSH_HOST}"`, StrictHostKeyChecking=yes) which runs an auto-deploy; there is no build/lint/test job, so nothing in CI gates a deploy. Only one workflow file exists in .github/workflows.
- Scalability limits (documented): "Run one instance only. The backend keeps an in-memory copy of the workspace and caches credentials per process" (POSTGRES_STORAGE.md Operations). Practical limits: memory = whole dataset x (db + structuredClone snapshot per save + fingerprint cache); single writer queue; 30 MB uploads buffered; event loop shared by PDF/OCR work; pool max 10; per-process caches (credentials, `storageCache`, `uploadIndex`, lifecycle memo, sync cache) mean horizontal scaling is impossible without refactor.
- Positive: graceful shutdown handler; idempotent `init()`; production-only removal of demo accounts (server.ts L1203-1210); auth hardening (default-deny policy table, same-origin check, upload sandbox headers, COS config validation, 10 review findings fixed in Phase B).

### Inferences
- Because the design assumes one node, the first scaling constraint is not CPU but the memory/latency of full-dataset saves and the lock queue; vertical scaling will hold until low-tens-of-thousands of rows per tenant x many tenants (not measured - inference).
- Error message leakage and lack of rate limiting on public endpoints (setup, exchange-code, invitation preview, public-status) are the cheapest security hardening wins.

### Gaps
- Did not inspect better-auth rate limit/session config in lib/auth.ts beyond the plugin portion read.
- Frontend nginx config was out of scope.

## 5. Test coverage and quality

### Takeaway
Backend tests exist and are of reasonable quality for the new infrastructure (DB facade, schema, object store, secrets, approvals, onboarding, normalized store) but none cover the 7.5k-line server.ts handlers except via two long e2e scripts that require a built bundle, Postgres and Playwright Chromium; nothing runs in CI.

### Cited Findings
- Unit test files in apps/backend/src (lines): db.pg.test.ts 131 (9 tests per handover), schema.test.ts 37, normalizedCore.test.ts 217, installationSettings.test.ts 45, mailTemplateStore.test.ts 47, invitationApproval.test.ts 115, partnerContact.test.ts 32, approvalRoutes.test.ts 185, objectStore.test.ts 95, secretBox.test.ts 68, onboarding.test.ts 132. Total 1,104 lines, ~48 `it/test` matches (grep). HANDOVER Phase G reports unit 78/78, e2e postgres 32, data-entry 41 scenarios, all green.
- E2E: normalizedCore.e2e.ts (580 lines, spawns server with isolated `legalio_test_*` DB, in-memory object store) and dataEntry.e2e.ts (204 lines, Playwright Chromium). Scripts: `npm run test:e2e:postgres`, `test:e2e:data-entry` (root package.json). Root `npm test` is an explicit list of files (not a glob), so a new test file is silently excluded unless added to package.json.
- Strength: tests hit a real PostgreSQL (TEST_DATABASE_URL) rather than mocks; targeted regression tests for race fixes (approval skip, delete after decision, read-query count "one query per table"); `onboarding.test.ts` covers password never in logs/response, file mode 0600, exit-1 on unreachable DB.
- Untested or only indirectly tested (no *.test.ts found): server.ts core CRUD handlers (partners/contracts/IOs/spendings/evaluations) beyond e2e happy paths, bulk-import (L6443, ~500 lines), `recalculateStatuses` / reminder logic, `coreDataStore.createCoreSaver` concurrency (only via normalizedCore tests), documentRoutes.ts (556 lines; only a frontend `documentsApi.test.ts` exists), organizationAdminRoutes.ts (814), authConsoleRoutes.ts (673), routePolicies.ts (344; policy exhaustiveness not unit-tested), rbac.ts (337), identity.ts (302), recordScope.ts (102), tenantPolicy.ts (204), lib/googleDriveSync.ts (729), lib/googleServiceAccountAuth.ts, lib/cheapOcrPipeline.ts (694), googleCredentials.ts, AI/Gemini wrappers, organizationReset.ts, organizationProvisioning.ts, serverMessages.ts. Coverage tooling: none configured (no c8/nyc/--experimental-test-coverage in scripts).
- Handover says COS setup-rollback cache restore and full `docker compose up` are not tested.
- CI: no workflow runs lint/build/test (only deploy.yml). The "gate" is manual per HANDOVER §2 (lint, build, test, build:sys, e2e), plus a manual "promise check" because TS is non-strict.

### Inferences
- Security-critical authorization lives in untested files (routePolicies/rbac/identity/recordScope are only exercised through e2e). A table-driven test that enumerates `app._router.stack` against `ROUTE_POLICIES` would guard the default-deny guarantee cheaply.

### Gaps
- No coverage numbers available; counts are from grep and line counts.
