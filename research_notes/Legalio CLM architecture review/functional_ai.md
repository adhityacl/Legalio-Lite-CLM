# Legalio CLM: functional capabilities, workflow correctness and AI usage (branch PostgreSQL, HEAD ce6ecd8)

Source convention: code facts cite repo-relative paths (line numbers from the checked-out tree, `apps/backend/src/server.ts` abbreviated `server.ts`). Web sources are linked. Review was targeted, not exhaustive: I did not read every route, run the app, or run tests.

## 1. Domain model, lifecycle states and server-side enforcement

### Takeaway
Legalio is broader than "lite": partners (with due diligence), evaluations, invoices/spending, contracts, service orders/IOs, amendments, termination, a document editor with versions/redlines, a separate approval flow, invitations, multi-tenant RBAC and org reset/provisioning. Date-driven statuses and approval transitions are enforced on the server (approvals with real concurrency guards); but the contract "approval status" (Draft/Review/Signed/Active) is a free label not tied to the approval workflow, and `PUT /api/contracts/:id` merges arbitrary client fields.

### Cited Findings
- Stated scope: partners with due diligence, evaluations and invoices; contracts and service orders with notice periods, renewal and termination; calendar; search; multi-tenant RBAC (admin/manager/editor/viewer) "enforced on the server"; Gemini AI; /sys console; en/id/zh — `README.md` (Highlights).
- Storage model: PostgreSQL only; core business data kept as in-memory collections (`db`) persisted by a single serialized writer with snapshot + one transaction (`createCoreSaver`, `coreDataStore.ts`); normalized child tables; every `saveDb()` writes the whole projection — `HANDOVER_POSTGRESQL_COS.md` §1 ("Model penyimpanan inti"), `server.ts:1262-1283` (`saveDb`).
- Contract lifecycle is computed, not user-set: `contractLifecycle()` returns status from end date, `expiryWarningDays`, auto-renewal, and termination date; modes are `normal | terminated`. A termination with a future date is "scheduled" and only becomes `Terminated` once the date arrives — `packages/shared/src/contractLifecycle.ts`.
- Termination validation is shared by form and API: requires a valid business date, not before start, not after end (`validateContractTermination`); server calls it in POST (`server.ts:4578`) and PUT (`server.ts:4755`). Termination evidence file validated by extension, base64 shape, magic bytes (%PDF-, ZIP, OLE2) and 10 MB cap — `apps/backend/src/contractTermination.ts`. Terminated contracts have auto-renewal forced off (`server.ts:4663, 4761`).
- Auto-renewal: `rollForwardAutoRenewal` silently moves `end_date` forward by the original term length (min 1 year, loop guard 200) whenever the end date is past — `server.ts:1586-1601`. There is no renewal-approval step or renewal record; the date just changes.
- Amendments: `document_type` ("Master Agreement" / "Agreement Addendum"), `parent_contract_id/number`, `change_summary`, `changed_fields` on the same contract entity (`server.ts:4529+`, AI prompt at `server.ts:3858+`); frontend has `AmendmentModal.tsx`. Amendments are separate contract rows linked by reference number, not a version chain that supersedes the parent.
- Due diligence: `status_dd` is derived by `computeDueDiligenceStatus(dd_documents)` on every partner write and upload/delete (`server.ts:2604, 3676, 3718`); checklists come from per-country/industry policy packs (`packages/shared/src/policy/*`, `tenantPolicy.ts`). I found no gate preventing a contract or IO from being created for a partner whose DD is incomplete (DD status is only passed to the AI redline prompt, `server.ts:4061`) — not exhaustively verified.
- Contract "approval status" (`status_approval`) is limited to Draft/Review/Signed/Active and normalised on write (`server.ts:4698, 4856, 6435`); nothing links it to the approval engine, and there is no e-signature integration (grep for docusign/e-sign finds only editor-history labels and legal text).
- Approvals (`approvalRoutes.ts`, 301 lines; tests `approvalRoutes.test.ts`, `invitationApproval.test.ts`): sequential 1-10 approvers, cannot approve own request, approvers must be active editor+ members, exactly one attachment (My Documents doc or upload PDF/DOCX/XLSX ≤10 MB), codes `OA-YYYY-NNNNN` allocated under a per-org Postgres advisory lock, fixed 48 h SLA (`SLA_MS`, "shortcut" comment), reject requires a comment. Decision uses a guarded `UPDATE ... WHERE status='pending' AND current_step=?` and requires `changes === 1` else 409 — blocks step skipping/double decisions. Decided approvals cannot be deleted; withdrawing returns doc to draft. `approvalStatusLock` makes `pending_review`/`approved` document statuses changeable only through approvals and forbids approved→draft — `approvalRoutes.ts:19-28, 145-300`.
- Approvals apply to editor documents (`contract_documents`), not to `contracts` rows; the approval flow sends no email (only three mail uses exist: verification, reminder, invitation — `server.ts:1510, 1678, 7492`). SLA is stored (`due_at`) but I found no escalation/reminder job.
- Documents: autosave versions, restore, compare, comments, metadata fields, redline panel; document PATCH/DELETE lock the row (`lockDocument`) and re-check status inside the tx — `documentRoutes.ts`, `HANDOVER_POSTGRESQL_COS.md` fix #3.
- Invitations: invite codes/emails with resend/revoke, accept via token preview, inviter must still be authorised; invitation mail via template — `organizationAdminRoutes.ts:737-763`, `server.ts:7487-7497`.
- Org provisioning/reset: `organizationProvisioning.ts`, `organizationReset.ts` (deletes COS objects after commit; returns 503 if COS unconfigured before deleting anything); onboarding (DB then superuser + COS probe) — `HANDOVER_POSTGRESQL_COS.md` §3/§4 Fase F.
- Mass assignment risk: `PUT /api/contracts/:id` spreads `...updates` from the body over the existing record (only `organizationId`, `termination_document` deleted before merge), so clients can set derived fields such as `days_remaining` or ids; status is later recomputed by lifecycle code, mitigating the date-driven part — `server.ts:4730-4745`. (Reviewed one route only; likely similar in IO/partner PUTs, not verified.)
- Tests present: approvals, invitations/approval, onboarding, normalized core, objectStore, secretBox, mail templates, schema, partner contact; e2e for normalized core and data entry. No unit tests found for `recalculateStatuses`/reminders or for AI routes (filename scan only).

### Inferences
- Server-side enforcement is strong for tenancy, RBAC and the approval state machine, weaker for business-lifecycle invariants (DD gating, contract approval label, field whitelisting on PUT).
- "Amendments" are linked records; there is no effective-dated obligation/value roll-up from parent + addenda, which CLM buyers usually expect (ContractSafe lists "linked amendments tied to the governing agreement" as a must-have — [ContractSafe](https://www.contractsafe.com/blog/best-contract-lifecycle-management-software-features-2026)). Legalio meets the "linked" part only by reference number.

### Gaps
- Did not verify IO/partner/spending PUT field whitelisting, spending/evaluation status rules, or the full bulk-import validation paths beyond enums (`server.ts:6432-6445`).
- Did not run the app, so UI behaviour of the lifecycle/termination flow is unverified.

## 2. Notifications and reminders: how notice-period reminders are actually sent

### Takeaway
Reminders are generated by `recalculateStatuses()` but nothing in the repo schedules it. There is no cron/interval; it runs only at server start (`init()`), on tenant-settings changes, org reset, bulk import, and via a manually-called superuser endpoint. Reminders are exact-day matches and send once per record+offset forever, so a restart-free server or a missed day silently loses reminders. This is the single most important functional defect found.

### Cited Findings
- `recalculateStatuses()` is called at `server.ts:1241` (end of `init()`), `5475` (`POST /api/cron/trigger-check`), `5922`, `6390` (reset), `6938` (bulk import). Repo-wide grep for `setInterval|cron|node-cron|scheduler` finds no scheduler in the backend, `compose.yaml`, scripts, or CI; only a Drive-backup `setTimeout` (debounce 5 s, `server.ts:564`), and frontend UI timers. The trigger endpoint is gated by `platform.database.optimize` ("all-organization system job") in `routePolicies.ts:120`, i.e. superuser only. An external caller would need a superuser session cookie.
- Reads also call `refreshContractLifecycles()` (cached 60 s, `server.ts:1708-1733`) which updates status/days_remaining but "without sending reminders" by design.
- Reminder rule: `settings.reminderOffsetsDays.includes(daysRemaining)` (default 90/60/30/14) — exact equality on the day count; dedupe by existing notification with same `parent_id` and type `Reminder {n}d` — `server.ts:1620-1640`. Consequences: (a) if the job doesn't run on the day the contract is exactly N days out, that reminder is never sent; (b) after an auto-renewal rolls the end date, the same `Reminder Nd` notification already exists for that parent so renewed cycles never re-notify; (c) notice-period deadline (end_date − `notice_period_days`) is only mentioned in message text — there is no reminder keyed to the notice deadline itself, the trigger is days-to-expiry.
- Delivery: in-app notification row always created; e-mail sent only if `smtpEnabled`, fire-and-forget (`.then(...).catch(console.error)`), no retry, no outbox, no delivery status stored; `is_sent: true` is set before sending — `server.ts:1648-1680`. `sendSmtpEmail` creates a new nodemailer transport per message with `tls: { rejectUnauthorized: false }` (certificate validation disabled) and a hardcoded Indonesian default from-name — `server.ts:1456-1500`.
- Recipients: record owner (`internal_pic` if it is an e-mail) + org-configured legal/finance notification address(es) + active org admins/managers — `reminderRecipients`, `server.ts:1597-1604`. Content localised en/id/zh with DB-stored mail templates (`mailTemplateStore.ts`, editable via `/api/mailer/templates`).
- Calendar: yearly document calendar from `features/calendar/calendarModel.ts` (contract start, cancellation notice, end, renewal, termination); notifications view `NotificationsView.tsx`, `/api/notification-logs` (read/delete).
- Notification rows are stored inside the in-memory `db.notifications` array and persisted by whole-projection saves; notification IDs use `Date.now()` + random 0-999.
- Handover §6 on risks and §9 on pre-merge test gaps (no scheduler is mentioned among the known issues) — `HANDOVER_POSTGRESQL_COS.md`.
- Market expectation: "Renewal alerts only count when a date becomes owned follow-up" with a lead time, named owner and next action — [ContractSafe 2026 features guide](https://www.contractsafe.com/blog/best-contract-lifecycle-management-software-features-2026); Juro lists automated reminders for deadlines/renewals/obligations — [Juro buyer's guide](https://juro.com/learn/clm-contract-lifecycle-management-software).

### Inferences
- In production the only reliable trigger is a restart/deploy (deploy auto-runs from `main`), so reminders effectively depend on redeploy cadence. Likely severity: high for a product whose core promise is "reminds you before notice periods run out" (`README.md`).
- Fix is small: an in-process daily timer (with advisory lock for multi-instance) running per-org in tenant timezone, using `<=` offset windows with a "sent offsets" ledger keyed by (record, end_date, offset), plus a notice-deadline reminder, retries and delivery status.

### Gaps
- I could not see the production server's own cron (deploy script lives on the Tencent Lighthouse host, not in the repo — `HANDOVER_POSTGRESQL_COS.md` §9), so an external crontab hitting the trigger endpoint can't be ruled out, but the endpoint requires a superuser session, which makes that unlikely.

## 3. AI usage: Gemini features, cost controls, prompts, privacy, failure handling, human-in-the-loop

### Takeaway
AI is used widely and mostly sensibly (structured JSON output, extraction results reviewed in a form before save, tenant-scoped and identifier-masked chat context, cached OCR, module/key switches). Cost control and safety gaps: no per-user/org rate limits or token budgets, chat stuffs the entire workspace JSON into every request, model fallback chain multiplies cost on failures, and the privacy posture depends on the Gemini tier the customer's key is on.

### Cited Findings
- Endpoints calling Gemini via `generateContentWithRetryAndFallback`: partner document parse + DD notes + review analysis (`server.ts:2273-2464`), evaluation review (`2719`), invoice/spending parse and review (`2996, 3136`), contract parse (`3858`), contract redline analysis (draft + saved, `4028-4258`), document AI redline (`4258`), AI template generation (`4416`), IO parse and review (`4923, 5062`), news ticker with search grounding (`1826-1837`), chat (`7102`), key/model test (`6033`). Frontend: `AIChatWidget.tsx`, `AIChatLauncher.tsx`, `ContractRedliningPanel.tsx`, `UploadDDModal.tsx`, `ContractCreatorView.tsx`.
- Gating: `ensureAiAvailable` requires the tenant `aiAssistant` module switched on and a configured key (403 `AI_DISABLED` / 400 `AI_NOT_CONFIGURED`) — `server.ts:2225-2236`. AI template generation is limited to admins/managers (`server.ts:4416-4421`). Gemini key is stored in settings/`process.env`; key is masked on read (`maskSecret`), but the handover lists encrypting `smtpPassword`, `geminiApiKey`, `refreshToken` in `app_settings` as explicitly out of scope — `HANDOVER_POSTGRESQL_COS.md` §1.
- Model handling: allowlist (gemini-3.8-flash default, 3.7/3.6/3.5-flash, 3.1-flash-lite, 3.1-pro-preview, 2.5-flash); the request body can choose a model among the allowlist (`req.body.model`); fallback chain tries up to 6 models sequentially with a 35 s timeout each (worst case ~3.5 minutes per request, plus no AbortController so timed-out calls keep running and billing) — `server.ts:830-935`. Errors are mapped to short actionable messages (`formatGeminiError`) but messages are in Indonesian regardless of tenant language.
- Cost controls present: OCR pre-processing `lib/cheapOcrPipeline.ts` (694 lines): inspects PDF, classifies digital_text / scanned_image / hybrid, extracts embedded text locally (pdf-parse), scores pages with a legal-keyword taxonomy and builds a reduced PDF of relevant pages for vision mode only when needed; SHA-256 hash caches task results (24 h TTL, max 300 rows, table `ai_ocr_cache`) and permanent plain-text transcripts reusable across features; contract-parse cache scoped per tenant (`contracts:${tenantId}`) — `cheapOcrPipeline.ts:49-147`, `server.ts:3858-3880`. Cache is global-count capped (300), so one busy tenant can evict others; transcripts share that pool (acknowledged in a "ponytail:" comment).
- Cost controls absent: repo-wide grep finds no `rate-limit`/`helmet`; no per-tenant usage metering, token budgeting, or spend cap; chat history from the client is forwarded unbounded (`server.ts:7236-7247`); document AI redline caps input at 40,000 characters (`server.ts:4263`), template brief 2,000 chars; contract draft fields 20,000 chars each.
- Prompt design: parse prompts are detailed, jurisdiction/industry-aware (org name, country, tax name, data-protection law, regulators, clause rules from policy packs), instruct "Use '' for any field not found", strict JSON schema with `responseMimeType: application/json`, explicit date arithmetic rules for end dates and evergreen (9999 sentinel), and "do not invent statute numbers" in redline/template prompts; redline quotes must be copied verbatim (allows UI anchoring) — `server.ts:3858-3925, 4258-4290, 4416-4445`. `internal_notes` prompt forbids commas for CSV safety (a hack that degrades summary quality). Template field labels are demanded in "short Indonesian label" regardless of tenant language (`server.ts:4440` approx.).
- Privacy of chat: only active-tenant, department-visible records (`visibleTo` filter) are sent; phone, e-mail, address, ID/tax numbers stripped, bank account masked via `maskTail`; system prompt tells model to refuse those — `server.ts:7109-7215`. However free-text fields (`internal_notes`, notes, contact_name, internal_owner e-mail) are sent unfiltered, and uploaded contract/DD/invoice documents are sent whole (or reduced pages) to Gemini for parsing, including personal data in them.
- Chat design limits: whole workspace as JSON in the system prompt for every message (no retrieval, no row cap, no truncation) — will exceed context or cost badly for orgs with thousands of records; temperature 0.2; answers computed by the LLM ("Compute sums ... strictly from the JSON") rather than tools — `server.ts:7203-7266`. The chat has no citations to record IDs in the answer format (IDs are in context, but the prompt doesn't require them).
- Human in the loop: parse endpoints return extracted fields to the client form, they do not persist (contract parse returns JSON; saving is a separate POST); redline analysis for a saved contract is persisted automatically as `redline_analysis` (`server.ts:4180-4195`) with timestamp; document AI redline returns suggestions with quotes; templates generated are drafts to review. So AI is advisory, but there is no per-field confidence/source-page citation in extracted values, a feature buyer guides ask for ("AI show its source text, keep a human review step" — [ContractSafe](https://www.contractsafe.com/blog/best-contract-lifecycle-management-software-features-2026)).
- Failure handling: friendly errors, retry across models, graceful 400 when AI is off; no queueing/async job for long OCR (requests block up to minutes inside the HTTP handler); no circuit breaker; AI results not validated beyond schema (e.g., dates not cross-checked vs. text except client-side review).
- Gemini data terms (external): unpaid-tier content may be used to improve Google products and reviewed by humans, and Google says not to submit sensitive/confidential/personal info there; paid-tier content is not used for product improvement (except specific caveats; EEA/UK/CH apply paid terms to all) — [Gemini API Additional Terms](https://ai.google.dev/gemini-api/terms) (primary source, via search snippet; secondary summary at [Simon Willison](https://simonwillison.net/2024/Oct/17/gemini-terms-of-service/)). The app places no check that the key is a paid-tier key; the settings text tells admins to use an AI Studio key.
- Analyst direction: AI is a core evaluation criterion across drafting, clause suggestions, risk identification, obligation extraction and analytics — [Bindlegal CLM market report 2026](https://bindlegal.com/resources/guides/clm-market-report-gartner-forrester/) (vendor-adjacent source); ContractSafe treats contract chat/AI review as nice-to-have and non-decisive versus repository fundamentals — [ContractSafe](https://www.contractsafe.com/blog/best-contract-lifecycle-management-software-features-2026) (vendor source).

### Inferences
- Priority AI fixes: add per-org rate limit + monthly token/page budget and usage log; drop `rejectUnauthorized:false`-style shortcuts around network calls only where relevant; abort timed-out calls; replace "send everything" chat with retrieval or function-calling over the DB; bound `history`; return page/quote provenance for extracted fields; run long OCR as background jobs; document a "use a paid-tier / Vertex key" requirement or enforce it in settings; localise error and template-label language.
- The cheap OCR pipeline is a genuine differentiator for a lite product (text-first, vision only for scans, hash caching).

### Gaps
- Did not read `AIChatWidget.tsx` in full (only confirmed it posts `history` to `/api/chat`) nor measure actual token consumption or the OCR page-selection quality.
- No pricing check for the named models (`gemini-3.x-flash`); model IDs are taken from the code and could not be verified against Google's current model list in this pass.

## 4. Google Drive sync, bulk import, export/portability, audit and activity logs

### Takeaway
Drive is a one-way file backup/folder-provisioning feature (not a bidirectional sync). Bulk import exists with enum/date validation. Portability is limited to per-view CSV/Doc exports and an uncertain full export; audit exists in two tiers, but the operational activity log is capped at 500 in-memory entries, which is weak for compliance.

### Cited Findings
- Drive: `lib/googleDriveSync.ts` (folder creation, hierarchical folders per org/partner, file upload, Sheets/Docs creation) and `lib/googleServiceAccountAuth.ts`; OAuth or service-account credentials stored encrypted (`googleCredentials.ts`, `secretBox.ts` AES-256-GCM, key HKDF from `BETTER_AUTH_SECRET`). Backup: COS objects are copied to Drive in a debounced (5 s) pass, tracked by an ETag stamp index in `APP_DATA_DIR/drive-backup.json` (a local file, lost if the container volume is not persisted) — `server.ts:500-575`, `HANDOVER_POSTGRESQL_COS.md` Fase C. Endpoints: `/api/google-integration/*`, `/api/tenants/auto-provision-folders`, `/api/contracts/export-google-docs`. `triggerAutoPushToGoogleSheet` is a no-op stub (`server.ts:1285`), so any former Sheets sync is gone.
- Bulk import: `POST /api/bulk-import` (`server.ts:6443-6950`, ~500 lines) with types for partners/contracts/IOs/evaluations/spendings; per-row validation with enums (`BULK_ENUMS`), invalid-date map, department override, one `recalculateStatuses()` per import (which, as noted, can also fire reminders for imported records); frontend `BulkImportView.tsx` and `packages/shared/src/bulkParse.ts` (+ test). Error messages are Indonesian.
- Export: frontend CSV helper `lib/csv.ts` and export buttons in Contracts/IO/Partners/Spending/Evaluation views; DOCX/print for the editor (`lib/docxGenerator.ts`, `editorDocx.ts`, `printDocument.ts`); Google Docs export endpoint. I did not find a full tenant data-export (JSON/ZIP of all records + files) endpoint; backup responsibility was explicitly handed to `pg_dump` and COS versioning (SQLite backup/restore UI was deleted) — `HANDOVER_POSTGRESQL_COS.md` §1/Fase A.
- Audit: `audit_log` table (actor, action, target, tenant/department, impersonated_by, metadata) written via `appendAudit` (24 call sites), queried with paging at `/api/organizations/:id/audit` and `/platform/audit` (`organizationSettingsStore.ts:443-470`, `organizationAdminRoutes.ts:778-802`); approvals audit submit/decision/delete. Operational "activity log" (`addActivityLog`, 33 call sites) stores user, role, action, module, description, IP, user agent but is truncated to the newest 500 entries in memory (`server.ts:1760-1765`) and surfaced in `ActivityLogsView.tsx`. Each activity log write triggers a full `saveDb()`.
- Org-level google/AI/SMTP settings and reset flows are logged; `GET /api/user/allowed-users`, sessions list/revoke exist (`/me/sessions`).
- Market expectation: "version control with an audit trail", "self-serve backups you can download on demand", custom roles/permissions with read-only access — [ContractSafe](https://www.contractsafe.com/blog/best-contract-lifecycle-management-software-features-2026).

### Inferences
- Activity-log cap of 500 plus whole-DB save per log entry is both a compliance and scalability issue; the structured `audit_log` should become the single record (with retention config and CSV export).
- Self-serve tenant export (JSON/CSV zip + files) is a cheap, high-trust addition for a self-hosted product.

### Gaps
- Did not inspect partial-failure semantics of bulk import (transactionality, per-row rollback) nor the Drive provisioning code beyond endpoint inventory.

## 5. Comparison with typical CLM feature set and highest-value gaps for a "lite" CLM

### Takeaway
Against 2026 buyer-guide must-haves (repository + search, reminders with owners, amendment linkage, RBAC, audit, backups), Legalio covers most of the repository/RBAC/audit layer and has unusual strengths (partner DD, evaluations, spend, policy packs per country/industry, trilingual UI, cost-aware OCR). Missing or weak: reliable scheduled alerts, e-signature, clause library/playbook, structured obligation tracking, integrations/API/webhooks, SSO, reporting/exports.

### Cited Findings
- Gartner's baseline CLM scope (review page updated Dec 2025, as summarised by a search result; direct page returned 403 to my fetch): requesting, creating, negotiating and approving, storing, reporting, searching, updating/renewing; obligation and compliance management under reporting — [Gartner Peer Insights CLM](https://www.gartner.com/reviews/market/contract-life-cycle-management).
- Analysts increasingly reward deep workflow integration (CRM, ERP, e-signature via APIs/connectors) over raw feature count; post-signature obligation tracking is a key differentiator; native e-signature is a common differentiator — [Bindlegal 2026 market report](https://bindlegal.com/resources/guides/clm-market-report-gartner-forrester/) (vendor-adjacent, treat as indicative).
- Template/clause governance trends: conditional logic in templates, clause-level versioning with jurisdiction tags, approval paths varying by deal size/region/risk — [SpotDraft](https://www.spotdraft.com/blog/the-buyers-guide-to-automated-contract-management-in-2026), [ZiaSign](https://ziasign.com/blogs/9-features-every-clm-platform-needs-2026) (vendor blogs).
- Lite-buyer guidance: start with the repository/alerts; defer intake, templates, approval routing, redlining, e-signature, CRM/SSO until tied to a use case this quarter; AI must show source text and keep a human review step — [ContractSafe](https://www.contractsafe.com/blog/best-contract-lifecycle-management-software-features-2026) (vendor source).
- Legalio inventory vs. gaps from code: 
  - E-signature: none (only a "Signed" label). 
  - Clause library / playbook: policy packs supply `clauseRules` to the redline prompt (`tenantPolicy.ts`), template list/AI generation exist (`/api/templates`), but no reusable clause library, fallback clause language, or conditional template logic (templates have `{{fields}}`). 
  - Obligation management: no obligation entity; only notice period, renewal, spending, evaluation scores, and AI free-text summary. 
  - Reporting/analytics: dashboard metrics (`lib/dashboardMetrics.ts`, `DashboardView/Overview`, treemap/hierarchy views, partner spending, exchange rates), no saved/scheduled reports. 
  - Integrations/API/webhooks: better-auth has an `apikey` hook (`BETTER_AUTH_API_KEY` env in `lib/auth.ts:211-214`) and Google login/Drive/Docs; no public REST API docs, no outbound webhooks, no CRM/ERP connectors, no Slack/Teams. 
  - SSO/SAML/OIDC/SCIM: only e-mail/password with verification and Google OAuth (`lib/auth.ts`); no SAML/OIDC/SCIM found in grep. 
  - Search: ILIKE across records (`/api/search`), no full-text of document contents/pg_trgm (explicit "shortcut" in handover §1). 
  - Security hygiene: SMTP TLS verification disabled, no rate limit/helmet found, SMTP password and Gemini key plaintext in settings (handover out-of-scope list), first-visitor-becomes-superuser window after deploy (handover §9 risk 4).

### Inferences
Highest-value gaps for a lite CLM, in suggested order:
1. Reliable scheduler for reminders (and notice-deadline alerts, owner assignment, snooze/acknowledge, delivery log). Lowest effort, directly tied to core promise.
2. Obligation / key-date model: a light `obligations` child table per contract (type, due date, owner, status) populated by AI extraction with human confirmation; ties to calendar and reminders.
3. E-signature through integration (DocuSign/Adobe Sign/local provider e.g. PrivyID/Peruri for ID market) or a webhook-based "signed copy" upload that moves status to Signed; avoids building native signing.
4. Public API + API keys + outbound webhooks (contract created/expiring/approved) and a tenant data-export; unlocks integrations without building connectors.
5. SSO (OIDC first; better-auth supports plugins) for enterprise adoption; SCIM later.
6. Clause library with approved/fallback text and playbook-driven AI review tied to `clauseRules`; show source quote and risk level.
7. Reporting: saved views, scheduled e-mail digest of expiring contracts/pending approvals, renewal pipeline report.
8. AI governance: usage metering and budgets, provenance for extractions, paid-tier/Vertex enforcement, retrieval-based chat.
9. Approval enhancements: e-mail notification to approver, SLA escalation, conditional routing by value/type, link to contract record.

### Gaps
- No pricing/adoption data for lite CLM competitors was collected; benchmark sources are mostly vendor blogs (ContractSafe, SpotDraft, ZiaSign, Bindlegal, Juro) and may carry commercial bias. The Gartner Magic Quadrant itself and Gartner page were not retrievable (403), so quantitative analyst claims were not verified.
- Did not benchmark specific lite-segment vendors' feature tables (e.g., G2) in this pass.
